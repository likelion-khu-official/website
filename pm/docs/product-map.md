# 제품 지도 — 표면·권한·소유권

> 사이트의 화면 층, 접근 주체, 데이터 소유권을 한눈에 보는 지도다. 상세 정책은 서비스 위키 [`정보구조와 권한`](https://github.com/likelion-khu-official/website/wiki/정보구조와-권한)이 정본이며, 이 문서는 구현 구조를 설명한다.

## 한 줄 정의

**3면 구조.** 공개(읽기·지원) · 멤버(부원 셀프관리) · 어드민(사이트 운영). 로그인은 멤버·어드민 표면 뒤에만 있고, 공개 화면은 인증 없이 사용한다.

## 왜 3면인가

- 공개 표면은 신입 지원자·타 동아리·기업이 멋사를 이해하는 얼굴이다.
- 멤버 표면은 부원이 자기 프로필·프로젝트·글을 직접 관리해 PM 한 명에게 콘텐츠 일이 몰리는 것을 막는다.
- 어드민 표면은 운영진이 계정 발급·콘텐츠 숨김·모집 운영처럼 공식 사이트의 품질과 운영을 책임지는 곳이다.

멤버와 관리자는 책임이 다르므로 인증 체계도 분리한다. 멤버는 학번 계정, 관리자는 초대받은 khu.ac.kr 이메일 계정을 쓴다. 모든 관리자는 같은 권한을 가지며 별도의 최고관리자·승급·강등은 없다.

## 세 표면

| 표면 | 대상 | URL | 인증 | 하는 일 |
|---|---|---|---|---|
| **공개** | 방문자 | `/*` | 없음 | 소개·프로젝트·블로그 열람, 지원폼 제출, 모집 알림 신청 |
| **멤버** | 로그인한 부원 | `/member/*` | 학번 + 비밀번호 | 내 글·프로필·참여 프로젝트 관리 |
| **어드민** | 관리자 | `/admin/*` | 이메일 + 비밀번호 | 멤버·관리자 계정, 콘텐츠, 운영진 소개, 모집 관리 |

공개 화면에는 로그인 링크를 노출하지 않는다. 멤버·어드민 화면은 주소로 진입하며 각 로그인 벽과 `noindex` 경계를 가진다.

## 접근 주체 × 권한

| | 방문자 | 멤버 계정 | 관리자 계정 |
|---|---:|---:|---:|
| 공개 콘텐츠 열람·지원 | ✅ | ✅ | ✅ |
| 내 글·프로필·참여 프로젝트 관리 | ❌ | ✅ | ❌ |
| 문제 콘텐츠 숨김 | ❌ | ❌ | ✅ |
| 멤버 등록·수정·비밀번호 초기화·오프보딩 | ❌ | ❌ | ✅ |
| 운영진 소개·모집·명단 관리 | ❌ | ❌ | ✅ |
| 다른 관리자 초대·삭제 | ❌ | ❌ | ✅ |

관리자 계정이 멤버 자기 콘텐츠 기능까지 자동으로 얻지는 않는다. 같은 사람이 두 책임을 모두 맡으면 멤버 계정과 관리자 계정을 각각 사용한다.

## 데이터 소유권

| 엔티티 | 누가 만들고 편집하나 | 운영 원칙 |
|---|---|---|
| **Member 계정·뼈대 정보** | 관리자 | 공개 가입 없음. 나가면 로그인만 막고 기록은 보존 |
| **Member 프로필 표현** | 멤버 본인 | 사진·입부계기 셀프 편집 |
| **Admin 계정** | 관리자가 초대·삭제 | 모두 같은 권한. 마지막 관리자는 삭제 불가 |
| **Post** | 멤버 본인 | 로그인 세션이 작성자를 보증. 즉시 게시, 문제 시 관리자 숨김 |
| **Project** | 참여 멤버 | 참여자만 수정·삭제. 문제 시 관리자 숨김 |
| **Staff 소개** | 관리자 | 공식 정보라 운영진이 관리 |
| **Comment** | 방문자 | 사전 승인 없이 게시, 문제 시 관리자 숨김 |

## 인증 모델

- 멤버와 관리자는 같은 JWT·쿠키 기반을 재사용하지만 계정 저장소와 로그인 식별자가 다르다.
- 멤버는 관리자가 발급한다. 아이디는 학번, 초기 비밀번호는 전화번호이며 첫 로그인 때 변경한다.
- 관리자는 기존 관리자가 이메일로 초대한다. 초대 링크에서 이름·비밀번호를 정한다.
- 초기 관리자만 배포 설정으로 시드한다. 이후에는 대시보드 초대를 사용한다.
- 관리자 권한은 `ADMIN` 하나다. 기수 교체는 새 관리자를 초대해 로그인을 확인한 뒤 기존 계정을 삭제하는 방식으로 한다.

## 일부러 안 하는 것

- 공개 회원가입
- 관리자 안의 파트장·대표 등 세부 권한
- 관리자 권한 승계·승급·강등
- 게시 전 승인 파이프라인
- 봇 가드·OTP·소셜 로그인

역할을 더 나누는 것은 실제 책임 차이 때문에 권한 경계가 필요해진 뒤에 검토한다. 이름만 다른 역할을 미리 만들면 화면과 운영 복잡도만 늘기 때문이다.
