# dev → main(prod) 배포 통과 기준 (초안 — 논의 중)

> 오너: 장찬욱(@cjang3285). **아직 확정 아님** — 팀 논의 후 확정되면 이 문구를 지우고 "확정" 상태로 갱신.

## 왜 이 문서가 필요한가

지금까지 dev→main 승격은 "적당히 안정되면 머지" 수준이었다. 그런데 2026-07-30 기준 실측해보니:

- **`main`이 `dev`보다 193개 커밋 뒤처져 있다.**
- **prod는 아직 `ddl-auto: update`(Flyway 도입 이전 방식)로 돌고 있다** — `dev`는 `#133`에서 Flyway로 전환(`ddl-auto: validate`)했지만 그 전환이 아직 prod엔 한 번도 반영된 적이 없다.
- 즉 **다음 dev→main 승격은 "마이그레이션 몇 개 추가"가 아니라, prod가 태어나서 처음으로 Flyway 체제로 넘어가는 컷오버**다 — `V1__baseline.sql`부터 지금까지 쌓인 마이그레이션이 그 배포 한 번에 실제 prod DB 위에서 전부 실행된다.

이 정도 규모의 첫 승격이면 "CI 통과했으니 머지"만으로는 불안하다는 문제의식에서, 통과 기준을 명시적으로 정해두려는 것.

## 배경 — 이미 있는 근거

- `backend/.claude/skills/db-man/SKILL.md`: `V1` baseline은 추정이 아니라 **실제 prod DB 사본을 받아 검증**해서 만들어졌다. main이 2026-07-24 이후 재배포된 적이 없어(`ddl-auto:update`가 그 사이 스키마를 추가로 바꿀 일도 없었으므로) 그 검증 시점 이후 드리프트는 없을 걸로 본다.
- `pm/docs/learnings.md`의 V6 사고(enum CHECK 마이그레이션이 CI green으로 stage에서 실패): 원인은 마이그레이션 SQL이 아니라 업그레이드 테스트 시드가 "이 컬럼에 대해 과거 모든 마이그레이션이 허용했던 값 전체"를 안 담았던 것. 대안으로 stage/prod 실 데이터를 CI에 들이는 건 PII 노출 때문에 기각됐고, 대신 "과거 마이그레이션 SQL의 CHECK 값 합집합을 정적으로 시드"하는 방식이 정답으로 확정됐다.
- CI(특히 유닛/통합 테스트)가 실제로 버그를 잡은 사례는 이 기록엔 없다 — 잡은 건 전부 Flyway 자체의 무결성 체크(버전 충돌, `migration-guard`) 같은 기계적인 것들이었다. "스펙대로 동작하는가"는 CI가 애초에 검증 대상으로 삼지 않는다.
- **2026-08-03 dry-run 실행 결과(아래 "실행 기록" 참고)**: 실제 prod DB 사본으로 마이그레이션 27개를 전부 적용 + `ddl-auto=validate` 기동까지 통과 확인. 부수적으로 발견한 것 — prod는 `recruitment_status` 1행을 빼면 `members`·`posts`·`applications` 등 전부 0행이라, 실사용자 데이터가 거의 없는 상태다. 과거 사고(V6 등)는 전부 "기존 실데이터가 새 제약을 위반"하는 유형이었는데, 지금은 위반할 데이터 자체가 없어 이론상 가장 안전한 타이밍.

## 통과 기준

**① CI 통과** — 당연한 전제. 별도 게이트라기보단 최소 문턱.

**② stage 체류 + 알람 무음** — 배포 후 일정 기간 OCI CRITICAL 알람(디스크·메모리·백업부재·git드리프트) 무발생. 다만 지금 서버 여유(2 OCPU/12GB에 트래픽이 적음) 때문에 알람 자체가 원래 드물어서 신호로선 약하다 — 비용이 거의 없으니 참고용으로는 유지, 이것만으로 "검증됐다"고 판단하지는 않는다.

**③ QA verification — 핵심 기준**
`pm/qa/criteria/<관점>.yaml`(given/when/then)과 `pm/qa/verification/<노드>.md`(pass/fail + 근거 + 확인방법 + 확인일자) 포맷으로, 이번에 승격되는 범위가 건드린 기능만 스코프로 확인한다(전체 회귀 스윕 아님) — 지금 벌어진 갭 기준으로는 어드민 단일 관리자 통합, 블로그, 지원폼, FAQ가 대상.

- **미해결**: 시나리오가 쌓이면 수동으론 감당이 안 된다 — 장기적으로 Playwright e2e로 자동화하는 방향에 팀 의견이 모였다. 다만 **레포에 현재 Playwright 스펙 파일이 0개**다(`E2eAdminSeedRunner`처럼 로그인용 고정 비번 계정 등 밑준비만 돼 있음). 자동화 자체를 별도 미션으로 발주할지 논의 필요.

**④ 마이그레이션 안전성**
- CHECK(enum) 값을 바꾸는 마이그레이션은 그 컬럼의 과거 모든 버전이 허용했던 값 전체를 업그레이드 테스트 시드에 포함하는지 확인 (이미 있던 규칙, V6 사고로 한 번 뚫렸던 지점이라 재확인 대상)
- **이번 승격 한정 특별 절차**: 첫 Flyway 컷오버라 리스크가 크다 — `db-man` SKILL.md의 "막히면" 절차(실제 DB 사본을 받아 마이그레이션 전체를 로컬에서 먼저 돌려보고 `ddl-auto=validate`로 기동 확인)를 **prod DB 사본**에 대해 배포 전 한 번 실행한다. `infra/scripts/backup_manager.py get`으로 최신 prod 백업을 받아서 진행 가능. **2026-08-03에 1회 실행 완료(아래 "실행 기록" 참고)** — 단, 이 결과는 그 시점 스냅샷이다. 실제 배포일이 그 뒤로 며칠 밀리면 그 사이 dev에 새 마이그레이션이 더 쌓일 수 있으니, **실제 배포 직전에 다시 한 번 돌릴 것.**
- **머지된 마이그레이션 파일 중 "검증용, merge 금지"라고 자체 명시된 게 새어 들어온 적이 있었는지 확인** (2026-08-03 발견, 아래 "실행 기록" 참고) — 이번 건 무해했지만 리뷰 단계에서 이런 파일을 거를 장치가 없다는 뜻이라, 승격 전 마이그레이션 디렉터리를 한 번 훑어 비슷한 게 더 없는지 확인.

**⑤ 롤백 준비**
- 배포 직전 "지금 prod에 떠 있는 이미지 태그"를 PR 코멘트 등에 기록 — 문제 생기면 `RUNBOOK.md` cheat sheet 그대로 그 태그로 되돌린다.
- 배포 직전 **수동 DB 백업 스냅샷**을 추가로 하나 떠둔다 — 매일 도는 정기 백업(18:00)과 별개로, 마이그레이션 실행 직전 시점 기준 신선한 복구 지점 확보(`RUNBOOK.md` "DB 복원" 절차 그대로 사용 가능). **단, 2026-07-31(#320)부터 삭제/변경형(재생성 패턴) 마이그레이션이 포함된 배포는 `cd.yml`이 이 사전 백업을 자동으로 실행한다** — 이번 승격에 포함된 마이그레이션 중 `V2`(재생성)·`V6`(행 삭제)·`drop_admin_role` 등이 해당돼 자동 백업 대상일 가능성이 높다. 그래도 **prod의 첫 컷오버라는 특수성 때문에 수동으로 한 번 더 떠서 이중으로 확보**하는 걸 권장.

**⑥ 환경변수 실값 확인 (`.env.prod`)**
- `RECRUITMENT_APPLICATION_FORM_READY` — 지원폼(#152) 완성 여부에 따라 사람이 의도적으로 관리하는 스위치. 코드 기본값(env 없으면 `false`)에 기대지 말고 서버에서 직접 확인.
- `SPRING_FLYWAY_CLEAN_DISABLED` — Spring Boot 자체 기본값이 이미 `true`라 없어도 안전하지만, 명시적으로 채워져 있는지 확인 권장.

**⑦ docker-compose 검토** — 구조 변경(새 서비스 추가 등)이 있으면 `docker compose up`이 그대로 될지 diff로 확인. 2026-08-03 기준 main↔dev 사이 diff는 `mem_limit`·포트 바인딩(`127.0.0.1`)·`JAVA_TOOL_OPTIONS` 추가뿐이라 안전하게 판단됨 — 다음 승격 시점엔 diff가 달라질 수 있으니 그때 다시 확인.

## 실행 기록

- **2026-08-03**: `ssh likelion-oci`로 prod DB 사본을 받아 로컬에서 `db-man` "막히면" 절차대로 dry-run 실행 — `baseline-on-migrate=true`/`baseline-version=1`로 실제 prod 조건을 재현, 마이그레이션 27개 전부 성공 + `ddl-auto=validate` 기동 통과 확인. 사용한 임시 테스트 파일·로컬 DB 사본은 확인 후 삭제(커밋 대상 아님, PII 우려로 안 남겨둠).
- **2026-08-03**: 같은 확인 과정에서 `cd_test_marker` 계열 마이그레이션 5개(`V20260731200500`~`V20260731204500`)가 파일 자체 주석("절대 dev/main에 merge하지 않는다")에도 불구하고 이미 dev에 머지돼 있는 걸 발견. 내용은 무해(더미 테이블 생성 후 자체 삭제, 실제 테이블 무관)해 이번 승격을 막을 사유는 아니라고 판단했지만, 리뷰 프로세스에 구멍이 있다는 신호로 위 ④에 남겨둠.

## 논의가 필요한 지점

1. ②의 체류 기간을 숫자로 못박을지, 아니면 참고 신호로만 남겨두고 강제 안 할지.
2. ③ QA 시나리오 자동화(Playwright e2e)를 별도 미션으로 지금 발주할지, 나중으로 미룰지.
3. ④의 "prod DB 사본으로 미리 돌려보기"를 실제 배포 시점에 누가 재실행할지(1회성 실행은 완료, 배포 직전 재확인 주체는 미정).
4. "merge 금지" 주석이 붙은 검증용 마이그레이션이 실수로 dev/main에 들어가는 걸 리뷰나 CI로 기계적으로 막을지, 아니면 리뷰어 주의로 충분한지.
