# claim-mission — 내 미션을 받아 끝까지 민다

팀원의 표면은 한 마디다: **"나한테 할당된 미션 수행하자."** 그 뒤의 배관(신원·PAT·gh·라벨·보드 item-id)은 전부 `scripts/`가 처리한다. 너(에이전트)는 스크립트를 부르고, 결과를 사람 말로 옮기고, 게이트에서 멈춰 사람에게 넘긴다.

> 대상은 초보일 수 있다. **gh 명령·토큰·필드 id를 사용자에게 보이지 마라.** 사용자가 볼 건 "누구세요? / 이 미션 맞아요? / 이대로 진행할까요?" 정도의 질문뿐이다.

---

## 계약 (어기면 QA에서 터진다)
불변식 전문은 `kb/contract.md`. 핵심만: 레포 `likelion-khu-official/website`, 보드 project #1. 라우팅 = **assignee**. 미션 뱃지 = 라벨 `roadmap` + 분야 라벨. 신원 = 레포 루트 `/.identity.local.yml`(키 `github_handle`·`pat`, gitignore됨). 이름·팀은 여기 안 적고 `pm/roster.yml`에서 handle로 파생.

---

## 사람에게 보이는 글 — 양식보다 실제 목소리

이 스킬이 쓰는 확인 질문·게이트·PR·코멘트는 문서 양식을 채운 결과가 아니라 **실제 사람이 동료에게 하는 말**처럼 읽혀야 한다.

- 사용자가 한 말과 미션 본문의 표현을 초안으로 삼는다. 말한 순서·걱정·확신하지 못한 부분을 지우고 기획 용어로 번역하지 않는다.
- 먼저 지금 무엇을 왜 말하는지 자연스럽게 설명하고, 알아낸 것과 네 판단을 이어서 말한 뒤 필요한 확인 하나만 부탁한다.
- `㉠ 리뷰포인트 / ㉡ 권장 답 / ㉢ 확인`, `Deliverable / Why / Done / Notes` 같은 고정 표면을 사용자에게 그대로 노출하지 않는다. 내부 점검에는 써도 외부 글은 필요한 만큼만 문단과 불릿을 쓴다.
- 받는 사람 이름을 알면 부르고, 그 사람과 이 미션에만 해당하는 구체적인 말로 쓴다. 이름만 바꾸면 다른 미션에도 그대로 보낼 수 있으면 다시 쓴다.
- 작성 뒤 “내가 실제로 동료에게 이렇게 말할까?”를 읽어본다. 지나치게 반듯한 보고서처럼 들리면 더 짧고 솔직하게 다시 쓴다.

단, 사람 말투는 맥락 생략이 아니다. 이 대화를 못 본 사람도 무엇을 왜 확인하는지 이해할 수 있어야 한다.

## 흐름

### Step 0 — 신원 확인
`scripts/check-identity.sh` 를 돌린다.
- `OK: <login>` → 신원 확정. 바로 Step 1.
- `NO_IDENTITY: …` → **바로 묻지 마라.** 먼저 아래 "Step 0-a 로컬 토큰 발견"으로 이 머신에 이미 있는 토큰을 찾는다. 없을 때만 인터뷰.
- `PAT_INVALID` / `HANDLE_MISMATCH` / `BAD_IDENTITY` → 사유를 사람 말로 옮기고, 인터뷰의 해당 단계(PAT 재발급 또는 handle 재선택)로 고쳐준다. **PAT 값은 절대 되묻지도, 출력하지도 마라.**

### Step 0-a — 로컬 토큰 자동 발견 (NO_IDENTITY면 인터뷰 전에 먼저)
`scripts/discover-token.sh` 를 돌린다. 이 머신에 이미 쓸 수 있는 GitHub 토큰(대개 `gh` 로그인)이 있으면 찾아 신원 파일을 자동으로 만든다 — 초보에게 PAT를 만들라고 하기 전에 마찰을 없앤다.
- `FOUND:<login>` → 머신에 유효 토큰이 있었다. `<login>`이 `pm/roster.yml`에 있는지 확인하고, 사용자에게 **"이 계정(<login>)으로 진행할게요, 맞죠?"** 한 번만 확인. 맞으면 `check-identity.sh` 재확인 → Step 1. (roster에 없거나 "아니오"면 그 파일을 지우고 아래 인터뷰로.)
- `FOUND:<login>:MISSING_PROJECT_SCOPE` → 위와 같되, **"이 토큰엔 보드 이동 권한(project)이 안 보여요 — 나중에 마감(Step 3)이 막히면 토큰에 project 권한을 더해주세요"** 라고 미리 귀띔.
- `NONE` → 머신에 쓸 토큰이 없다. 아래 인터뷰로.

### Step 0-b 인터뷰 (로컬에 토큰이 없을 때만 — 아주 친절히)
1. **안심시킨다:** "처음이시네요. 딱 한 번만 신원을 잡아두면 다음부턴 '나한테 할당된 미션 수행하자' 한 마디면 됩니다."
2. **누구세요?** `pm/roster.yml`을 읽어 **handle이 있는 멤버만**(디자인·null 제외) 선택지로 제시하고 사용자에게 고르게 한다(있으면 `AskUserQuestion` 등 선택지 툴을, 없으면 그냥 텍스트로 물어본다). 고른 사람의 `handle`을 확정. **본인이 목록에 없으면**(디자인처럼 GitHub 없음, 또는 명부 밖) → "claim-mission은 GitHub 기반이라 이 방식의 대상이 아니에요. 디자인 작업은 카톡·Figma로 받습니다"라고 친절히 알리고 **여기서 멈춘다**(억지로 진행 금지).
3. **GitHub PAT 만드는 법** (단계별, 초보 기준):
   - 브라우저에서 https://github.com/settings/tokens/new 로 간다 (로그인 필요).
   - Note에 아무 이름(예: `likelion-claim`). Expiration은 적당히(90일 등).
   - **스코프 체크: `repo` 전체 + `project`** 두 개. (이슈를 읽고 보드 카드를 옮기려면 이 둘이 필요하다.)
   - 맨 아래 **Generate token** → 나오는 `ghp_…`(또는 `github_pat_…`) 문자열을 복사. 이 화면을 벗어나면 다시 못 보니 지금 복사.
4. **저장:** 레포 루트에 `/.identity.local.yml`을 만든다. 내용은 딱 두 줄:
   ```
   github_handle: <고른 handle>
   pat: <붙여넣은 토큰>
   ```
   이 파일은 `.gitignore`에 있어 **커밋되지 않는다**(개인 비밀). 이름·팀은 여기 안 적는다 — roster에서 파생.
5. **검증:** 다시 `scripts/check-identity.sh`. `OK`면 통과. `HANDLE_MISMATCH`면 2번(사람 선택)이 틀렸거나 다른 계정 토큰 → 바로잡는다. `PAT_INVALID`면 스코프 빠졌을 확률 → 3번 다시.
6. 통과하면 곧바로 Step 1.

> PAT를 대화에 다시 노출하지 마라. 파일에 쓸 때 외엔 값을 입에 담지 않는다.

### Step 1 — 내 미션 가져오기
`scripts/fetch-my-mission.sh` → `count=<N>` + 이슈 JSON.
- **0개:** 아직 배정된 미션이 없다. "PM(@xhae123)이 아직 안 던졌거나, 다른 사람에게 갔어요." — 끝. (초조하게 만들지 말 것.)
- **1개:** 그 미션으로 진행. 본문에 담긴 PM의 걱정·원하는 결과·경계를 원래 표현을 살려 짧게 옮기고 "이 미션부터 같이 볼게요. 맞죠?" 한 번 확인. 고정 소제목이 없다고 임의로 양식을 만들지 않는다.
- **N개:** 제목으로 목록을 보여주고 어느 미션부터 할지 고르게 한다(있으면 `AskUserQuestion` 등 선택지 툴을 쓴다).

### Step 2 — 수행: R → P → 【RP 게이트】 → I → Q → 【IQ 게이트】  (순서 고정 · 게이트는 하드 스톱)

먼저 `kb/loop.md`(루프 규약)·`kb/mindset.md`(우리 규모 개발 철학)를 적재. 각 페이즈에서 렌즈 kb를 **필요할 때만** 얕게 읽는다. **순서를 지켜라 — 게이트를 통과하기 전엔 다음 단계로 못 넘어간다.**

> ⚠️ **미션을 채간 사람은 이 미션의 맥락을 거의 모른다고 가정하라.** 매 단계 첫 줄에 *지금 뭘·왜* 하는지 쉬운 말로 한두 문장 설명하고 진행한다. 전문용어는 풀어서. **사람을 시험하지 마라 — 일은 네가 하고, 사람은 게이트에서 검토만 한다.**

1. **R — research** *(자율)* → `kb/research.md`. 미션 본문에서 PM이 걱정한 것·원하는 끝 상태·지켜야 할 경계를 기준으로 코드·계약(`shared/`)·주변을 읽어 "무엇을 해야 하는가"를 파악한다. 명시적인 `Done` 체크박스가 있으면 함께 쓴다. **미션이 Sub-task면 상위 Story와 그 Story가 가리키는 위키 스펙도 먼저 읽어라.** 사람에겐 지금 무엇을 왜 확인하는지만 쉬운 말로 짧게 알린다.
2. **P — plan** *(자율)* → `kb/plan.md`. 알아낸 것으로 **어떻게 할지** 구체 계획(바꿀 파일·접근·순서).
3. **【RP 게이트】 — 채간 사람 본인의 셀프 검토** *(PM 보고 아님)*
   PM에게 올리는 자리가 아니라, 채간 사람이 방향을 한 번 보고 승인하는 자리다. 지금까지 알아낸 핵심, 그래서 택한 접근, 아직 남은 가정을 **한 통의 짧은 동료 메시지**로 쓴다. 네 권장 판단까지 말한 뒤 "저는 이 방향으로 가면 된다고 봤어요. 걸리는 게 없으면 그대로 진행할게요"처럼 확인 하나만 받는다. 번호가 붙은 검토 양식을 보여주거나 사람을 시험하지 않는다. OK면 바로 I로, 걸리는 점이 있으면 R/P를 고쳐 다시 확인한다.
4. **I — implementation** *(자율, 게이트 없음)* → `kb/implement.md`. 승인된 계획대로 구현. Q까지 멈추지 말고 민다.
5. **Q — qa** *(자율)* → `kb/qa.md`. 미션이 부탁한 결과와 경계를 근거로 대조 검증한다. 명시적인 `Done` 체크박스가 있으면 한 항목씩 확인하고, 스코프 크리프는 잘라낸다(`kb/mindset.md`).
6. **【IQ 게이트】 — 채간 사람 본인의 셀프 검토** *(역시 PM 보고 아님)*
   요청받은 걱정이나 목표를 어떻게 닫았는지, 무엇으로 확인했는지, 남은 위험과 산출물 위치를 자연스럽게 설명한다. 체크박스는 미션에 실제 완료기준이 있을 때만 근거와 함께 쓴다. 네 판단을 먼저 말하고 "이 정도면 처음 걱정하신 부분까지 닫혔다고 봐요. 이대로 마감할까요?"처럼 확인한다. OK면 Step 3, 부족한 점이 나오면 I로 돌아간다.

> **게이트 원칙:** 두 게이트 다 채간 사람 본인의 검토다. 사이 구간은 AI가 자율로 일하고, 게이트에서는 맥락과 권장 판단을 사람 말로 충분히 설명한 뒤 확인 하나만 받는다. 판정 기준은 미션 본문의 부탁·원하는 결과·경계이며, 명시적인 완료기준이 있으면 그것도 포함한다.

### Step 3 — 마감 (IQ 게이트 통과 후 · 반드시 실행)

**미션은 연 사람이 닫는다.** IQ를 통과하면 곧바로, 순서대로:
1. **산출물 마무리** — 코드 미션이면 `scripts/create-pr.sh "<제목>" "<본문>"` (브랜치 push + 리뷰용 PR, base=dev). 반환된 URL을 사람에게 "리뷰용 PR 올렸어요" + 링크로. 코드가 아니면 미션이 요구한 산출물(문서·URL 등)을 확정.
   > **PR 본문 원칙 — 팀원이 리뷰어에게 직접 말하듯 쓴다.** 미션에서 실제로 걱정하거나 원했던 표현을 이어받아, 무엇을 왜 바꿨고 어디를 봐주면 되는지 3~5줄로 말한다. `Summary / Testing` 양식을 자동으로 세우거나 파일 목록과 작업 과정을 늘어놓지 않는다.
2. **결과 상자 기록(필수)** — 이 미션 상자의 `pm/missions/<n>-<slug>/result.md`를 채운다: **산출물**(PR 링크·무엇이 남았나), **결정**(이 미션에서 갈린 판단), **배운 것**. 다음에도 쓸 통찰은 `pm/docs/learnings.md`로 **졸업**시킨다(상자엔 이 미션 고유 결과만). 코드 미션이면 이 기록도 같은 브랜치에 커밋·push해 PR에 포함됐는지 확인한다. **빈 stub로 두고 이슈만 닫지 마라** — 이 상자가 다음 세션 AI가 먹을 맥락이고, 비면 "닫혔는데 무엇을 남겼는지 모르는" 미션이 된다. (PM측 `mission` 스킬의 "결과 정리 / 미션 닫아"와 같은 일 — 코드 미션은 연 사람이 여기서 한다.)
3. **미션 닫기** — 결과 기록이 PR/산출물에 포함된 것을 확인한 뒤 `scripts/close-mission.sh <n> "<마감 코멘트>"` → 보드 카드 Done + 이슈 close. 마감 코멘트도 자동 문구가 아니라, 처음 부탁받은 일을 어떻게 닫았는지 팀원이 직접 말하는 한두 문장으로 쓴다. PR을 올렸으면 링크를 함께 남긴다.
4. **현황은 자동 롤업 — 손으로 안 고친다.** 보드 Status는 끝나지 않은 `Todo`와 끝난 `Done`만 쓴다. 미션(Sub-task)을 닫으면(위 close-mission) 이 미션이 sub-issue로 달린 상위 Story의 진행률이 GitHub에서 자동으로 갱신된다. 예전의 손유지 상태 트리(`pm/features`·README)는 폐기됐다 — 상태 색을 칠할 일이 없다. (그 Story의 하위 미션(Sub-task)이 이번으로 다 닫혔으면 Story도 닫히고, 그 Story가 속한 테마 Epic의 Story가 전부 닫혔으면 PM이 project-board/tidy-missions로 Epic을 닫는다 — 팀원은 여기까지 안 해도 된다.)
5. **결과 요약** — 사람에게 쉬운 말로: *뭘 했고 · 산출물이 어디 있고 · 미션은 닫혔다 · 트리 노드가 어떻게 바뀌었다.* 끝.

> 이 전체 흐름(신원 → 페치 → 수행 → 마감)은 **오차 없이 순서대로** 돈다. 게이트는 하드 스톱, Step 3의 닫기는 필수 실행 — **건너뛰지 마라.**
