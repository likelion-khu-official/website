# P (plan) — 조사 결과를 실행 계획으로 구체화한다

R에서 파악한 요구와 제약을, RP 게이트에서 검토할 수 있는 실행 계획으로 좁힌다. 새로운 요구를 임의로 만들지 마라 — 필요하면 R로 되돌아갈 일이다.

## 렌즈
- **파일 단위로.** 어떤 파일을 새로/고치나(가능한 기존 파일 수정 우선 — mindset). 각 변경이 미션에서 부탁한 어떤 결과에 대응하는지 매핑한다.
- **가장 작은 경로.** 부탁받은 결과를 만드는 최소 변경. 미래 확장·설정·훅 넣지 않는다(YAGNI).
- **계약 변경이면 표시.** `shared/` 타입을 바꿔야 하면 그건 다른 팀에 영향 → PM 게이트 사안일 수 있다(ask-pm 고려).
- **검증 방법을 미리 정한다.** 부탁받은 결과를 Q에서 무엇으로 확인할지(테스트/실행/화면)를 계획에 적어둔다. 명시적인 완료기준이 있으면 항목별 근거도 정한다.

## 산출
변경 파일 목록 + 각 변경↔부탁받은 결과 매핑 + Q 검증 방법. (P까지는 자율 구간이고, 다음은 I가 아니라 RP 게이트다.)

## 함정
- 계획이 부탁받은 범위를 넘어 커짐(스코프 크리프) → 잘라낸다.
- "이 구조가 더 멋져서" 리팩터 끼워넣기 → mindset 위반. 미션 밖.
