# PM — 운영 하네스

> 김우진(PM·조직장)의 운영 베이스.

## 시작 전 읽기
1. 루트 `CLAUDE.md`
2. `pm/docs/`: `learnings.md` → `brief.md`

## PM 책임
- **결정** — 무엇을·왜. 방향·범위·우선순위.
- **운영** — 일정 조율, 막힌 것 해소, 스쿼드 통합. 진행은 GitHub 이슈(로드맵).
- **콘텐츠 수급** — 사진·소개글·자료를 운영진과 협의해 확보(전담 없음). 그림자 크리티컬 패스.
- **배운 것 관리** — *다음에도 쓸 통찰*이 생기면 `pm/docs/learnings.md`에. 결정·상태는 안 쌓음.
- **미션 박스 관리** — 미션 하나 = `pm/missions/<번호>-<슬러그>/` 상자(`proposal`→`log`→`result`). 제안·진행·결과의 정제된 맥락을 쌓는다(GitHub 복붙 아님). 운영은 mission 스킬.
- **Epic = 미션의 출발점·도착점** — 미션(Story)은 GitHub의 한 **Epic 이슈**(사용자 향 기능 슬라이스, 예: "방문자가 프로젝트 목록을 볼 수 있다")에 sub-issue로 걸린다. 미션의 무엇·왜는 그 기능의 **위키 스펙**에서 파생한다. 그 Epic이 아직 없으면 발주할 때 만든다(mission 스킬이 지연 생성·링크). **새 미션은 아직 미션이 안 달린 Epic**(또는 위키에 스펙은 있는데 Epic이 없는 기능)에서 고른다 — 위키(스펙) ↔ Epic(현황) ↔ 미션(전진)은 한 몸. 진행률은 Epic이 하위 미션 상태로 **자동 롤업**하니, 예전처럼 상태 색을 손으로 유지·갱신하지 않는다(그 손유지가 2026-07-15 트리가 며칠간 거짓말한 사고의 원인이었다 — 그래서 손유지 상태 트리 자체를 폐기했다). 상세는 mission 스킬.

## 무엇을 learnings에 남기나
- 남긴다: 다음에도 쓸 **통찰**(팀·제품·기술·과정에서 배운 것), 왜가 드러나게.
- 안 남긴다: 일회성 결정·기술 스택 선택·진행 상태·대화 과정. (진행은 GitHub)

## 미션 이슈 발주 (필수 3단계)
미션을 GitHub 이슈로 쏠 때 `gh issue create`는 **① Projects 커스텀 필드(Team·시작일·목표일)도, ② 상위 Epic 연결도** 자동으로 안 한다(이슈는 보드에 자동 추가되고 Status=Todo까지만). 그래서 발주는 **항상 3단계가 한 세트**:
1. `gh issue create …` (제목·본문·라벨·어사인) — 라벨은 `roadmap` + 팀 라벨(미션 뱃지, claim-mission이 이걸로 찾는다).
2. `pm/scripts/mission-fields.sh <issue#> <디자인|프론트|백엔드|인프라> <시작 YYYY-MM-DD> <목표 YYYY-MM-DD>` — Team·시작일·목표일 세팅.
3. **상위 Epic에 sub-issue로 건다** — 이 미션이 전진시키는 기능 슬라이스의 Epic 이슈 밑에 방금 만든 미션을 연결한다. Epic이 없으면 mission 스킬이 그 기능의 Epic을 먼저 만든다. 배관: `pm/scripts/link-subissue.sh <Epic이슈#> <미션이슈#>`.
2·3번을 빠뜨리면 미션이 보드/Epic 밖에 떠서 안 보인다(2번 누락은 2026-07-05 실제 발생). 발주했으면 반드시 3단계까지 — Epic 지연생성 규칙은 mission 스킬.

## 성공 기준·검증 (`pm/qa/`)
`pm/qa/`는 두 갈래로 나뉜다 — 섞지 않는다.
- **`criteria/<관점>.yaml`** — 성공 기준. given/when/then(기대 동작). 스펙이 안 바뀌면 안 바뀐다. TDD의 테스트 코드에 해당.
- **`verification/<노드>.md`** — 검증 결과. 그 기대가 지금 실제로 성립하는지(pass/fail/not-run) + 근거. QA 때마다 갱신. TDD의 테스트 실행 로그에 해당.

작성 규칙(안전장치 문구·근거 형식·fail 정의·보안 규칙)은 `pm/qa/GUIDE.md`. **Epic 이슈의 `## 완료기준`이 이 GWT를 검증 ID(예: PROJ-002)로 참조한다** — 성공기준이 "됐다"의 실질 판정 기준이다(Epic 롤업은 이슈/PR 기반 진행상태, 검증은 실제 동작 확인). GWT 정의 자체는 `criteria/`에 산다(이슈에 복붙하지 않는다 — drift 방지). 현재는 **익명 방문자 관점만** 구축됐다(`pm/qa/criteria/일반사용자.yaml`) — 로그인 이후(멤버·어드민·최고관리자) 기능은 아직 GWT 커버 대상이 아니다.

핵심 불변식 셋 (상세는 GUIDE):
- **결과 숫자는 verification이 단일 원본** — Epic 이슈엔 검증 ID 참조만, ID별 pass/fail 표를 복사하지 않는다.
- **fail = "기대 동작 ≠ 실제 동작"만** — 이슈-코드 불일치는 verification의 "정정" 근거로, 스펙이 의도한 공백은 pass+note로 분리한다.
- **보안성 fail은 공개 문서에 재현 정보 금지** — 요지만 적고 상세는 비공개 전달, 수정 미션 최우선 발주.

**범위 한정 — 안전장치.** 이 검증은 given/when/then이 코드·API·화면에서 기대대로 동작하는지, 즉 **기능 동작만** 판정한다. 디자인 품질(비주얼 QA)·보안 침투 테스트·성능·접근성은 범위 밖 — 별도 프로세스가 필요하다. verification 문서마다 이 문구를 상단에 명시한다.

## Git — 푸시 방식
- **기본 푸시 대상은 `dev` 브랜치다. `main`은 특별한 지시가 있을 때만.** 왜 — `main` = prod = 운영 배포라, main에 꽂으면 곧장 운영에 나간다(인프라 CI/CD: dev=stage, main=prod). 그래서 main 직접 푸시는 위험하고, 특별 지시가 있을 때만 한다.
- **PR은 김우진의 지시가 없는 한 올리지 않는다 — dev에 직접 푸시한다.** PM 운영(하네스·문서·미션 박스)은 혼자 도는 작업이라 PR 게이트가 오히려 마찰. PR이 필요하면 김우진이 그때 명시한다.
- **PM 하네스 산출물(스킬·`pm/` 문서·미션 박스·`ops.md`·이 `CLAUDE.md` 등)은 전역 "*.md 커밋 제외" 규칙의 예외** — 하네스가 곧 PM 운영의 결과물이라, 일반 작업처럼 **dev에 곧바로 커밋·푸시한다**(매번 별도 지시 불필요). `main` 푸시와 코드(FE/BE/infra) 변경은 여전히 지시·팀 규칙을 따른다.
- **`pm/` 아래 무언가 수정·생성되면 그 턴 안에 바로 dev로 커밋·푸시한다 — 서 있는(standing) 규칙, 매번 "푸시해" 지시를 기다리지 않는다.** (2026-07-14 김우진 재확인) PII(`pm/applicants/` 등 실명·개인정보)만 예외 — 이건 커밋하지 않고 사람에게 알린다.
- 비밀은 절대 커밋 금지 — `*.local`·비밀번호는 레포 밖에.
